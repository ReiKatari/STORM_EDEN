## 2. Стандарт оформления релизов GitHub (Release Body Guidelines)
При создании или обновлении релизов GitHub (`PATCH` / `POST` к GitHub Releases API) строго соблюдать следующую структуру:

### Правило 1: Запрет дублирования заголовка и префикса 'v'
- **Никогда не добавлять заголовок первого уровня `# H1` с названием проекта и версией в начало описания релиза**, так как GitHub отображает название и версию в заголовке страницы релиза автоматически.
- **Никогда не указывать букву `v` перед номером версии** (писать `4.8.8`, `Релиз 4.8.8`, а не `v4.8.8` или `Релиз v4.8.8`).

### Правило 2: Запрет подписей автора в релизах
- **Запрещено добавлять фразы вида `Собрано и опубликовано автором...` в конце или теле релиза**.

### Правило 3: Структура описания релиза
```markdown
> 💡 **Релиз {version}** — *{Краткое описание назначения утилиты/проекта}*

---

### 🚀 Ключевые изменения и улучшения
- 🌟 **[Компонент / Функция]**: [Описание ключевого изменения]
- 🌟 **[Компонент / Функция]**: [Описание ключевого изменения]

<details>
<summary><b>📋 Полный список изменений (нажмите, чтобы развернуть)</b></summary>

- 🔹 **[Пункт 1]**: [Детальное описание]
- 🔹 **[Пункт 2]**: [Детальное описание]

</details>

<details>
<summary><b>🌐 English Changelog (click to expand)</b></summary>

- 🔸 [English notes if available]

</details>

<details>
<summary><b>📦 Файлы и вложения к релизу (нажмите, чтобы развернуть)</b></summary>

- 📁 **Прикреплённые файлы**: Исполняемые файлы, инсталляторы и архивы доступны в секции **Assets** ниже.
- 🛡️ **Контроль целостности**: Все бинарные файлы собраны из официального исходного кода и проверены перед публикацией.
- 💻 **Установка**: Скачайте соответствующий архив/инсталлятор из списка Assets и следуйте стандартным инструкциям.

</details>
```

### Правило 4: Форматирование Markdown внутри `<details>`
- Вокруг тегов `<summary>` и `</details>` обязательно оставлять пустые строки (двойной перенос строки), чтобы таблицы, списки и вложенный Markdown рендерились GitHub без сбоев разметки.
- Не разбивать существующие Markdown-таблицы и блоки кода на плоские списки.

## 3. Стандарт оформления документации README.md

### Правило 1: Заголовок первого уровня (H1)
- Главный заголовок **всегда центрируется**: `<h1 align="center">НАЗВАНИЕ ПРОЕКТА</h1>`.
- **Запрещено использовать иконки, эмодзи, логотипы и дефисы с уточнениями в H1**.

### Правило 2: Оформление разделов и формулировки
- Все заголовки второго уровня оформляются жирным шрифтом: `## **Название раздела**`.
- **Запрещено использовать фразы вида «Доработан ReiKatari»**.
- Если проект является форком, **обязательно чётко указывать базовый эмулятор / утилиту** (например, форк эмулятора Nintendo Switch **Eden**, на базе **Citron** и **Yuzu**; форк эмулятора **MelonDS** и **DeSmuME**; графическая оболочка **CHDMan** от команды **MAME** и т.д.).
- **Запрещено добавлять блоки «Безопасность и цифровые подписи» и «Авторы и лицензия»**.
- **Запрещено выводить дерево структуры директорий репозитория**.
- В разделе **Благодарности** приводить исчерпывающий список всех авторов, команд и библиотек **строго без URL-ссылок**.
- В инструкциях по установке указывать реальные имена файлов: `<Имя>_<версия>.apk`, `<Имя>_<версия>_LEGACY.apk`, `<Имя>_<версия>.zip`, `<Имя>_<версия>_Setup.exe`.
